# oMLX 预填充显示修复 · 端到端记录

2026-11-14，本机 oMLX 0.7.4.dev1，模型 `DeepSeek-V4.1-Flash-1017-Abliterated-MLX`（会话在用、全程未换模型、未卸载）。截图都是 TFPanel 主屏预览窗口的 `--capture` 输出（程序自己按当前 View 重画，960×640），数据来自真实请求，不是样例回放。

## 根因

oMLX 的 `prefilling` 行在带缓存时：

- `prompt_tokens`：整个提示长度
- `cached_tokens`：缓存命中长度
- `total`：这次还要算的**新** token（≈ `prompt_tokens − cached_tokens`）
- `processed`：其中已经算完的**新** token

原适配器按早期假设把 `processed` 当成“全部已算量”，写 `filled = max(cached, processed)`。缓存命中多时 `processed` 小于 `cached`，于是：

- 进度条停在 `cached / prompt`，看起来不动（实际是 `cached + processed`）；
- 采集器按 `filled` 增量算预填充速度，`filled` 不增长就没有第二个进度点，速度一直是 `—`。这正是“有时不显示速度、偶尔才显示”；切到下一个请求时又会重新走“只有已用时”的降级画面，看起来像“一开始正常、后面不显示”。

实测一行（提示 33,348 / 缓存 24,576 / 新算 8,772）：

```json
{"processed": 8192, "total": 8772, "cached_tokens": 24576,
 "prompt_tokens": 33348, "speed": 0.0, "eta": null}
```

正确进度是 `(24576 + 8192) / 33348 = 98.2%`，原逻辑显示 `24576 / 33348 = 73.7%`。

## 修复

`Engine.swift` 的预填充行：`total` 是“剩余新 token”时（`total < prompt` 且 `cached > 0`），
`filled = cached + processed`；否则（无缓存、或 `total` 就是提示长度）沿用 `max(cached, processed)`。
这样同时兼容 oMLX 新旧两种字段口径，且无缓存的九段实录输出逐拍不变。

另外，`Collector.swift` 在只有第一个进度点时，先用“从到达算起的新 token 平均速度”（`filled − cached` ÷ 已等待秒数）给预填充速度；下一个块到了再换成块间实测值。这样进度行一出现就有速度，不再等第二个块。

新测试：`OmlxAdapterTests.test_有缓存时进度按缓存加已算`、`CollectorTests.test_只有一个进度点且已等待时先给平均速度`。

## 仍未覆盖的窗口

oMLX 的进度行只在**第一个预填充块算完**（本模型 8192 token）后才出现；在那之前引擎不发布提示长度、已算 token 或速度。适配器只能显示“已用时”。这次截图取的是进度行出现之后的画面——速度与进度从出现起持续到预填充结束。若要让第一块期间也有数字，需要引擎把 tracker 更新提前到块开始或缩小块；属于 oMLX 侧，不在本仓改动范围。
