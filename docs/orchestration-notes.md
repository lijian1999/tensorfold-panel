# 编排记录：本地模型（Qwen3.8 Flash Next，经 pi）干活的表现

给编排者（Claude）看的。每派完一个任务记一行，用来逐步建立“什么样的任务用什么思考档位、拆多大”的标准。

## 环境

- 5 路并发时单流约 25 tok/s，合计约 125 tok/s；单流独占约 60 tok/s。所以并发时同一个任务要 2 倍多的时间。
- `pi -p` 只在结束时输出，思考是隐藏的。派工用 `--mode json` 接格式化脚本，在终端标签里实时显示；必须 `< /dev/null`，否则会挂住等标准输入。
- pi 的 `maxTokens` 是 131072，单轮思考没有上限。

## 目前的经验

- **健康的节奏是“轮数多、每轮短”**（J、D）：写一点、跑一下、改一点。**危险信号是单轮几万 token**（C、E、G）：模型在闭门推演。G 虽然成功，但那一轮 4.5 万 token 占了一半时间。
- **成败不取决于说明的长短，而取决于规则是否互相牵连**。F 的说明比 E 还长，但每条规则各管一处，一次做对。E 的规则前后依赖（忙碌段、一轮、归属输出），模型想把所有组合都推演清楚再动手。
- **需要模型自己钻研底层机制的事，直接把做法给它**（C 的导入钩子：仓库里有验证过的草稿，应当让它照着写）。
- 时限：后台时限给到上限，按“有没有进展”判断卡没卡住，不按墙上时间。

- **low 和 medium 在“闭门思考”上没有明显差别**：low 档下 C 仍然单轮 4.3 万 token，E1 单轮 2.4 万。off 档会把同样的纠结变成几百次小命令。所以档位管不住这个问题，管得住的是任务本身：别让它有可钻的牛角尖。
- **模型一旦认定某条路（例如“标准库这里有坑”），不会自己回头**。发现它偏了要尽早停掉，由编排者验证事实后给一份很小的纠正任务（C2），不要让它在原任务里继续。
- 停掉一个 pi 之后要确认进程真的没了再重派。第二轮里有一次 `pkill` 没生效，两个执行者同时改同一批文件一个多小时。
- 环境：从 App 的终端标签里连不上 Spark（局域网访问被拦），pi 必须从 Bash 工具启动；终端标签只用来 `tail -f` 实时输出。

- **管思考的提示词没用**（“不要推演”“一次思考不要太长”）。统计了思考里“我要停下来开始写”这类句子：没加提示时每万字 0.4–1.9 次，加了之后 0.3–1.5 次，没有变化；I 轮询反而 16 次引用提示词原话、密度升到 2.6。原因：在思考里“停下来”本身也是思考；卡住它的是某个确认不了的点（无解的验收命令、认定的“坑”、没想清的测试设计），不是没有决心。已从 `AGENTS.md` 删掉，换成管决定的规则。
- 上下文长度（2026-10-05 复盘后不再当作要管的因素：任务定义好了就让模型自己处理；K 到 20 万也通过了；当时看图慢还有图片让缓存失效的原因，已修复）。当时的观察：成功的任务最大上下文 4–11 万 token；16 万以上出现思考退化成重复碎片（I）、撞上限报错（H，17.9 万提示 + 预留回复超过 26 万）、长时间不动文件（E1，23 万）。长思考留在历史里，上下文越滚越大，是自我加强的循环。看图尤其占上下文。
- **验收命令不能有模糊或无解的地方**：I 卡在我写的 `… | head -1` 上（管道提前关闭会让 Python 打印一句去不掉的提示）和“6 行左右”。

- **“编排者先通读、定位问题，再给一份小的纠正任务”是目前最稳的方式**（C2、I2、H2 都一次通过）。H 的对照图由编排者自己在 Spark 上出图、自己看（6 张），比让执行者看图快得多：执行者两小时没改一行，编排者十分钟定位到“刻度数字没调用”。
- **low 对 medium**：同一模块上 E1（low）和 E2（medium）都做对了；E2 用时更短、单轮思考更短（最长 1.5 万对 2.4 万），但 E2 是在现成代码上补充，起点更容易，不能算干净的对比。目前的数据不支持“low 不如 medium”，也不支持反过来。
- 进程可见性：pi 把自己的进程名改成 `pi`，按命令行找不到；停一个任务要按父进程（`run_pi.sh`）找。派工脚本和日志放在仓库的 `.orch/`（不进 git），放 `/tmp` 会在重启时丢。
- 目标模式下可以用完成通知：结束一轮时如果有应用能跟踪的后台命令在跑，停止钩子不会拦，命令退出时自动唤醒。所以用一个后台看门命令（`.orch/wait.sh`）等任务结束即可，不需要反复挂起。

- **规则互相牵连的任务也可以一次做对，前提是编排者先自己把规则跑通**（V2、V3）。做法：编排者在草稿目录里写一份参考实现，在真实数据上验证设计规则（这一步改掉了设计文档里三处错误）；说明里把规则写成逐条可照做的步骤；把“每一步之后应有的状态”做成数据文件随任务给出，测试的骨架代码直接写进说明。执行者要做的就只剩“照规则写、对不上就看是哪一步”。E（第 1 版采集器）失败时缺的正是这些：规则只有文字，没有能逐步对照的预期。验收时拿参考实现逐次比对，比读测试更可靠。
- **说明里每个预期数字都先在草稿实现上跑出来再写**（V2–V5 共约 120 个数字，执行者没有遇到一处“说明和实际对不上”）。
- **并行任务之间共用的数据格式改动（这次是快照样例加字段）单独拆成一个小任务先做**，后面的并行任务就不会互相等对方的文件。
- **录制数据的采样节奏要和程序实际的轮询节奏一样**。这次录的是 0.05 秒一次、回放按 0.1 秒，而程序空闲时是 0.25 秒一次；一个和 0.25 秒有关的阈值在回放里全过，到实机第一轮就错了。参考实现验证设计规则时，要按真实节奏（忙时 0.1、空闲 0.25）再回放一遍。
- 4 路并发时各任务互不干扰的条件：每份说明的检查命令只跑自己的测试模块，并写明“同时有别人在改哪些文件”。

## 派工约定（第二轮起）

通用的做法已整理成用户级 skill `orchestrate-local-pi`（`~/.claude/skills/orchestrate-local-pi/`），以它为准；本文只保留这个项目的派工记录。

- 思考档位从 `low` 起步。验收发现逻辑错误才升档，只是慢不升。
- 说明用“第一步、第二步”的动作来组织，每步带一条要运行的命令；不写劝告式的工作方式。
- 规则互相牵连的任务分步交付（每步有自己的测试范围），不为了并发而拆。
